# Agents

The + in the notch, or New Agent in the page, opens one field: the mission, in one sentence. An agent is a personality and a role: it belongs to no app and has no connectors at creation, and any agent can be plugged into any window. On Return or a chip, the agent hatches at once with a color from the request, and Muse Spark writes the chosen agent: name, role, personality, voice, a greeting and an off-limits line, a hue and an accessory. The agent gets its own folder. Once plugged into a window, the agent reads that window's title and Accessibility text when it changes, keeps a short understanding in its folder, and shows a one-line bubble in its voice. An off-limits window is never read. A click on the notch or on an agent opens the agents page, a native window that follows the Mac's light or dark mode: agents grouped by Needs you, Working and Idle, the credits left, a conversation with the selected agent (messages, replies and its actions, with links and Undo) and an inspector with its mission, what it works on, its connectors and what it can do without asking. Closing the page gives the focus back to the app that had it. An agent with a mission and a scope works on its own in the background: on a light timer or when it is dragged onto something, it runs a read-only check, decides with Muse Spark whether there is work, acts with its tools inside its scope, and writes what it did to its journal. An agent still being written has an empty name: the reader skips it, and an unfinished one is removed at the next launch.

## Sub-features

- `agents-propose`: 3 proposals, each a name, a role and a pitch, that name no app.
- `agents-create`: the written agent, saved as `Agents/<id>/AGENT.md`, the readable card: identity, targets, `allow`, `deny`, `read_only`, `born_from`, `leave_when`, and the job. `state.json` beside it holds what changes while running: its window and its check. A hand edit that does not parse keeps the last good version in `.AGENT.good` and raises a need.
- `agents-source`: when the user creates an agent, the maker gets the open windows, connected services and catalogue, and picks a source. A window is proposed in one question and nothing is read from it until the user says yes; a request that names it counts as yes. `--probe-hands create` and `--probe-hands confirm` run this without the page.
- `agents-questions`: an agent's `ask_user` and `stuck` come back to Bean with its result, or wake Bean if the run was not handed off. Bean answers, reassigns or asks the user. A user talking to an agent is answered by it directly. Irreversible abilities ask directly. A block never raises a question: it is a line in the report.
- `agents-first-move`: on a first start with nothing at all, one call offers up to 3 things from window titles and connected services, as a question with options. Once, and gone at the first request.
- `agents-memory`: `memory/notes.md` holds what one agent learned, at most 1,500 characters, and `user.md` in the data folder holds what the user prefers, at most 800, shared by all agents. The `memory` tool adds, changes and removes entries; a write over the limit fails and the agent makes room. Both show at the start of each run and stay fixed during it, before the agent's state, so the cached prefix holds. `corrections.md` and `goals.md` are written by code from what the user answered or asked, and memory does not hold them.
- `agents-read`: reading on AX notifications and a 5 s poll, at most one Muse Spark call every 12 s, only when the title or text changed. Writes `memory/window.md`, sets the activity to `reading` then `idle` with the bubble. Logged to `agents.jsonl`.
- `agents-offlimits`: a window whose app, bundle id or title matches off limits is never read; the bubble is the agent's off-limits line and no model call is made.
- `agents-unplug`: unplugging stops the watch, deletes `memory/window.md` and clears the activity.
- `agents-mission`: `write` takes only the sentence and fills the card: mission, targets (only names literally in it), and, with no target, a question posted to the chat. A target can be added in the chat. With no target the agent does not act.
- `agents-settings`: `worker.targets`, `connectors` and `abilities` come from what the agent really has, with no per-service code. Abilities are classified from connector tools and `--help` (safe, outward, irreversible, the riskier when unsure); irreversible ones are off. The guard enforces each one. `connectors.json` and `abilities.json` live in the agent's folder.
- `agents-guard`: every command goes through a guard in code: one plain command, nothing outside the scope or off limits, no secrets, no interpreters. Reads cannot change anything; acts cannot merge, deploy or delete unless the mission allows it; pushes name HEAD, never the main branch. Refusals are journaled.
- `agents-work`: a run reads its check, stays silent if the output did not change, asks `AgentWorker.decider` (Strands 2B first when the user turned it on: a score at or below 0.40 stays quiet with no model call, anything else goes to Muse Spark, which decides alone when Strands is off or missing), then works with `run_shell`, `act`, connector tools, and ends with `finish` (saving its new check) or `stuck` (mood `needsYou`).
- `agents-sessions`: `session_drive` starts or continues a coding session in a worktree of a repo in the agent's targets, through the stand-in; `session_act` accepts its work and `session_close` ends it. `$1` per session at most.
- `agents-stop`: a runaway stop in code, `AgentWorker.runawayStopUSD`, ends an agent's work for the day. It is internal: no page, prompt or message shows money.
- `agents-standin`: `ClaudeStandIn` runs Claude Code in stream-json with `--permission-prompt-tool stdio --restricted`, in a worktree of a repo in scope. It answers `AskUserQuestion`, each tool request (guard first, then Muse Spark), and the end of each turn: reply, accept or refuse. Goals come from `goals.md` in the agent's folder. It drives only sessions Bean starts, and reads nothing from the user's transcripts.
- `agents-chat`: `worker.send` writes the user's message to the journal (`said`), answers with one model call, and runs the work loop only when the request needs action or a lookup inside the scope; the answer lands as `replied`. A message matching off limits gets the agent's off-limits line with no model call.
- `agents-tone`: every prompt carries the Writing section of `Templates/base.md`. Agents have no voice of their own.
- `agents-drop`: a drop writes to the journal and always runs, waiting if the agent is busy, with the window as its trigger. With no target, no permission, a window it cannot read or a spent budget, the agent says why (mood `needsYou`) and makes no model call.
- `agents-pause`: Pause stops ticks, window reads, drops, chat and any model call, also during a run: `ModelClient` refuses while paused. `BEAN_PAUSE_AFTER=<s>` on `bean agents say` proves it. Its reply uses the language detected on the device when the detection is sure, otherwise English.
- `agents-errors`: model errors read as plain sentences (key refused, no network, no credits), set `worker.modelProblem`, journal once per cause and set `needsYou`.
- `agents-needs`: `needs.json` holds what waits on the user (stuck, decision, problem, budget, setup). While one is open the mood stays `needsYou`, across a relaunch, until it is answered or solved.
- `agents-decisions`: `memory/decisions.jsonl` records each answer a stand-in gives: question, answer, why, confidence, permission or judgment. Below 0.6 confidence it stops the session and asks with options and a recommended pick. `worker.correct` writes `memory/corrections.md`, which every later prompt reads. `worker.away` sums up decided, waiting, done and cost.
- `agents-brain`: Bean is the one loop. Its tools: `list_windows`, `create_agent`, `attach_agent`, `detach_agent`, `hand_off`. Agents act only when dropped on a window or handed work; handoffs go to both journals (`handoff`, `to`), and Bean reports once. Only Bean ticks, and only after take over.
- `agents-channels`: an attached agent has `window_read`, `window_controls`, `window_act` (Accessibility, no mouse or keyboard) and `app_script` (the app's own AppleScript, only that app, never to the front). The app's commands become abilities from its `sdef`; any irreversible word is refused unless that ability is on.
- `agents-context`: every chat and work prompt carries the guide to the app, the agent's state and the user's profile (`user.json`, learned from the chat only). The user's language is followed; shared places keep theirs.
- `agents-enforced`: one agent per window and no repeat of work are checked in code in `attach_agent` and `hand_off`: a task like an earlier one, on a window whose content has not changed, returns the earlier result with no model call. An agent without a window says so; requests with no window go to Bean.
- `agents-journal`: `journal.jsonl` in the agent's folder: id, at, kind, did, why, result, link, undo, undoCommand, undoes. `worker.undo` runs an undo command through the guard.
- `agents-card`: `onAgentClick(id)` opens the card under the notch.

## How to get to it (user POV)

- Click Bean in the notch while it rests.
- Click a proposal, or type in the field and press Return or Create.
- Drag the agent onto a window (creatures side), then click it to open its card.

## Driving it with bean

Preconditions:

- Baseline from [README](./README.md). A Muse Spark key (`MODEL_API_KEY` in the environment, the repo `.env` or the Keychain). Accessibility granted to the built Bean for reading.

- **Propose.** `bean agents propose` prints the app list sent to Muse Spark and the proposals. Run `agents-free`: 3 proposals in 10.6 s (Stack Juggler, Signal Sifter, Lab Buddy), none naming an app.
- **Create.** `bean agents create "<request>"` prints the folder tree and its files, and the agent id. Run `agents-free`: Jip, cap, hue 0.07, `connectors: []`.
- **Read.** `bean fixture "<title>" <file>` opens a window the run owns and prints its pid; `bean agents read <agent-id> <pid> 55` plugs the agent into it, prints every activity change and `window.md`, then unplugs. Edit `<file>` during the run (a first line `title: …` sets the window title) to see a second understanding. Run `agents-read`: a failed build understood in 4.3 s, the passing build 26 s later in 3.9 s, `window.md` deleted after unplug.
- **Off limits.** The same read with `BEAN_OFF_LIMITS=<word in the title>`. Run `agents-read`: one `offLimits` line, no `understood`.
- **Guard.** `bean agents guard <agent-id> read|write|undo "<command>"` prints `allowed` or the refusal, with no model call. Run `agents-gh`: 24 cases as expected.
- **Work.** `bean agents work <agent-id> [runs]` runs the loop and prints the decision, the calls, `journal.jsonl` and `AGENT.md`. With `BEAN_DRY_RUN=1` the model and the reads are real and no act runs. Run `agents-gh`, dry: found `gh`, read 4 diffs, drafted 4 reviews in 30.8 s; the second run stayed quiet. Without it the acts are real: only on a test repo with the user's go. Run `agents-gh`, real: 4 comments, a quiet second run, then PR #5 reviewed and marked ready for $0.023. Run `agents-linear`, real, scope one test ticket and the test repo: `linear__get_issue`, `session_start`, commit, push, draft PR #5, comment on VER-38 with the link.
- **Connector write.** `bean agents connector-write <server__tool> '<json>'` makes one real write, to create or clean up test data. Only with the user's go.
- **Credits.** `.claude/skills/verify/bin/credits` prints the estimate: the console balance in `~/Library/Application Support/Bean/credits-base.json` minus `ledger.jsonl`, written by `ModelClient` on every call with its tokens and the published price, whatever the run's data dir.
- **Stand-in.** `BEAN_SESSION_MODEL=haiku bean agents standin <agent-id> <repo> <clone-url> "<task>"` starts and drives a session the run owns. Run `agents-standin`: question answered from `goals.md`, `git push origin main` refused, branch pushed, accepted after 3 turns, $0.037 Muse Spark and $0.004 Claude; `cat /etc/hosts` refused. Never point it at a user's running session.
- **Chat.** `bean agents say <agent-id> "<text>"` sends a message and prints the end of the thread. With `BEAN_DRY_RUN=1` no act runs. Run `agents-chat`: small talk in 2.7 s, "4 PRs open" read for real, merge and another repo refused in its voice, off limits stopped, an agent with no mission says so.
- **Settings.** `bean agents settings <agent-id> [<ability-id> on|off]` prints the three lists, or turns one ability on or off. `bean agents guard` shows the effect on a command, `bean agents guard-tool <agent-id> <server__tool> '<json>'` on a connector tool. `bean agents connect <agent-id> <name>` connects a `toConnect` connector. Run `agents-settings`: a GitHub agent lists `gh pr merge` off and `gh pr comment` on, a Linear agent lists `linear__save_comment` on, with no per-service code.
- **Take over.** `bean agents adopt-bean` creates Bean with its mission, paused. `bean agents say BEA00000-0000-0000-0000-000000000001 "Take over… You can work on <ticket> and <repo>."` adds the targets and the goal, resumes it and runs. Run `agents-takeover`, real: VER-39 read, session driven, PR #6 opened, ticket moved to In Review, reported in the chat, force push and hard reset refused, $0.13 Muse Spark and $0.008 Claude.
- **Drop, pause and errors.** `bean agents read <agent-id> <pid> 45` is the drop path. `BEAN_PAUSED=1` on `read` and `say` shows the pause. `MODEL_API_KEY=wrong BEAN_IGNORE_ENV_FILE=1` or `BEAN_BASE_URL=http://127.0.0.1:9/v1` on `say` and `work` shows the errors. `bean agents settings <agent-id>` prints spend and the model problem. Run `agents-audit`.
- **Tasks from a plan.** With a `PLAN.md` in a test repo, `bean agents say <bean-id> "Take over… The tasks are in the PLAN.md of that repo."` works through it. `bean agents needs <id>` prints the mood, needs and decisions; `needs <id> answer <text>`, `needs <id> correct <text>` and `needs <id> away <minutes>` drive the rest. Run `agents-plan`, real: PRs #7 and #8, a license question with options, then #9 after the answer; a corrected answer was used by a new session.
- **Bean's goal.** Give your test windows titles with your run id and filter on that id: another session's test windows match `swift-frontend` or `Monday`, and Bean will write into them. `BEAN_WINDOW_FILTER=<word>` limits `list_windows` to the windows whose app or title contains that word, for example `swift-frontend` for the run's fixtures. With two fixtures open, `bean agents say <bean-id> "Prepare Monday's client meeting…"` creates and attaches agents, hands work between them and reports once. Run `agents-brain`: Robin read the thread, Nora filled the brief through Accessibility, read back from the window. In the app: `bean tap`, `bean fill "<goal>"`, `bean press "Send"`, with `BEAN_WINDOW_FILTER` and two `onscreen` fixtures. Run `agents-live`: `creatures.jsonl` shows `lift` from `bean`, `drop`, `perched` for each agent, and `after.png` shows both on their windows with the brief filled.
- **App abilities.** `bean agents app <bundle-id> <app-name>` lists what the app's dictionary gives; add a script to see if it is allowed. Nothing runs.
- **Strands filter.** Off by default: it runs third-party code, so the user turns it on in the menu bar (`usesStrands`), or `BEAN_DECIDER=strands` in a test. The install lives in `~/Models/strands-decider` (`venv`, `hf`), or `BEAN_STRANDS_HOME`. Never run the real package without Rayan's confirmation. Lifecycle tests use a stub home with its own `venv/bin/python` and `venv/bin/strands-decider`: `bean agents strands-up [seconds]` holds the server, and `pgrep -f strands-decider` is empty after `BEAN_STRANDS_IDLE` seconds, on quit, on TERM and after `kill -9` on Bean. The server gets only PATH, HOME, HF_HOME and HF_HUB_OFFLINE, and binds to 127.0.0.1. Run `strands-real` on the real package, with Rayan's go: 73 cases, see the numbers it prints; a fresh work sentence scored 0.448 and the lowest work case 0.47, so 0.40 leaves room. 0 of 31 missed still allows a real miss rate up to about 9%. Memory about 4.1 GB while up, ready in about 3.5 s, stopped after 5 min idle.
- **Take Over.** `bean agents takeover <agent> <window> <seconds>` runs the real worker and reader; change the fixture's file meanwhile. With no change Bean makes no model call. Run `agents-tick`: changed at 17:51:04, Bean decided at 17:51:30 and handed work over.
- **Create in the app.** `bean launch`, move the cursor onto the notch, `bean press "New agent"`, `bean fill "<text>"` (move the cursor into the field first), then Return. The drop splits off Bean and hangs under the notch while it forms; its greeting shows under it once Muse Spark has written it. Capture with `screencapture -R` around the notch. Run `ux-live2`: the split in `split-strip2.png`, the greeting and the hint in `greeting.png` and `greeting-hint.png`.
- **Plug and card.** `bean fixture "<title>" <file> onscreen` opens a visible window the run owns; `bean dragout <agent> swift-frontend` perches the agent on it and `agents.jsonl` shows `plugged` then `understood`. A click on the perch (`bean perch <agent>`, then `click.swift` on its center) opens the card; `bean press "Unplug"` logs `unplugged` and removes `memory/window.md`; `bean press "Delete"` then `bean press "Delete <name>"` removes the folder. Run `agents-ui`: Pip understood the chat in 4.9 s.

## Gotchas

- In any run with `BEAN_DATA_DIR` set, `list_windows` returns nothing unless `BEAN_WINDOW_FILTER` is set. Use a filter such as `swift-frontend` for test windows. `*` means every window on the Mac, and their titles reach the model.

- An offscreen fixture can lose its Accessibility windows after a while: `agents.jsonl` logs `unreadable`. Use `onscreen` fixtures, under the lock, for a full proof.

- `bean agents work` without `BEAN_DRY_RUN=1` acts for real. Use a test scope, with the user's go.

- `bean agents read` needs an agent created in the same `BEAN_RUN_ID`, since agents live in the run's data dir.
- The CG window title needs Screen Recording; without it the title comes from AX only.
- Electron apps expose their text only after `AXManualAccessibility` is set on the app, which the reader does.

The page opens on Bean, at the top of the sidebar; its chat is the main conversation. Its agents are listed under it, each with its window (app icon and title), or "Drag me onto a window" when it has none. Bean's thread ends with a While You Were Away card: waiting, decided for you, passed between agents, done, stopped, spend. A `handoff` journal entry shows who passed what to whom. An open `needs` entry keeps the agent in Needs you and replaces the composer with a question card: options, a recommended pick, Other and Skip. Budget and problem needs show as banners. Judgment decisions show as "On your behalf" rows with Why and Correct; permissions are only counted. One notification per need, remembered across a relaunch, none while the page is key. Abilities with deeper siblings are hidden. Budget warns at 80% and shows the pause at 100%. No copy assumes a developer.

Drag: from the notch or from a sidebar row's drop onto a window. The drop stays on the window until sent home or removed, and the window stays in Works on; the agent reads it and runs on its content, and chat can answer from what it read. Removing the target clears that reading. Releasing over the page changes nothing. Proof: drop on a fixture window, check `agent.json` attachment, `mission.json` targets, `memory/window.md`, and a chat reply that quotes the fixture.

The inspector renames an agent (not Bean); the card follows. While the page is open Bean is a regular app: Dock icon, Cmd-Tab, menus, Cmd-N, Cmd-0 for Bean. The page opens on the display under the cursor and floats over the active Space, a full-screen app's included; Esc, unless a text field has text, closes it and returns to the previous app. It takes its own full-screen Space only from the menu or Control-Command-F. Test runs do not save its frame.

The notch never talks: a missing key opens the page, whose banners carry the buttons for the key, Accessibility and a model failure. A click on Bean in the notch opens Bean's chat. When Bean attaches an agent it calls `worker.onAttach(id, windowNumber)`, and the drop flies from the notch to that window.

One window per agent: dropping it on another window replaces the old one in Works on. Cmd-[ and Cmd-] move between agents. A need can carry `consequences`, keyed by option, shown under each option.

With the page in front, a drag from a notch head hands focus to the previous app during the drag; the page comes back in front at the end.

Bean's chat shows what it does, the windows open on this Mac with Put an Agent Here, and what agents just chose to do or to wait. When paused, Put an Agent Here attaches a free agent, or a new plain one, without a model call. New agents take a free color from a palette; the inspector's Look section sets color and mark, and a color set there is kept by the one-time recolor.

Settings is an entry in the page's sidebar (Cmd-comma), with AI, Off Limits, Permissions and What Bean Sees (Cmd-I): the front window's text, apps, windows, browser tabs, commands, and every gate decision with its score and time. It reads only while that tab is showing. Bean's page shows the last four decisions.

## Prompts, offline

`bin/prompt-check` renders every prompt against `bin/fake-model.py`, with no paid call, and prints the hash of system and tools per call, the tuned rules in `evals/rules.txt`, the money words, the six defects and the refusal table in `evals/refusals.json` against `evals/refusals-baseline.json`. `evals/baseline/` keeps the prompts as they were before the templates. `evals/run-understanding.py <binary> <run id> [cases]` replays the understanding cases, and it is paid: one call per case.
